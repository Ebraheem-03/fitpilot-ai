# Evaluation reports

Reports here are generated by the eval runners and committed as evidence (FR-02, FR-13, blueprint §10). `plans-<prompt_version>.{md,json}` comes from `make eval-ai` (`uv run python -m app.services.evaluation.plans`, services/api); only the section between the NOTES markers is hand-written.

## What the CI guard covers, and what it doesn't

`test_prompt_files_have_a_live_eval_report_recording_their_hash` (`services/api/tests/test_eval_plans.py`) fails when the prompt files and the committed live report disagree. It compares `prompt_sha256` (`app/services/plans/prompts/__init__.py`) with the hash recorded in `plans-<version>.json`. Edit a prompt file and the guard stays red until the live eval is rerun for a new `PROMPT_VERSION`.

The hash covers **only the three prompt files**, `<version>.{system,user,repair}.md`, with CRLF normalised to LF (the prompts folder also pins `*.md text eol=lf` in its `.gitattributes`). It does **not** cover:

- the **catalogue rendering**: the exercise table inserted into the system prompt comes from `data/exercise-catalog`, so adding or changing an exercise changes what the model sees without changing the hash;
- the **plan schema** and its limits (`app/schemas/plan.py`: sets, reps, rest, exercises per day), which are substituted into the template and sent as the JSON schema;
- the **validation rules** (`services/plans/validation.py`) that decide valid, repaired or `needs_review`;
- the **settings**: `LLM_MODEL`, `LLM_REASONING_EFFORT`, `LLM_MAX_COMPLETION_TOKENS`, and the provider.

A change to any of those needs a rerun of `make eval-ai` and a review of the report even though the guard stays green. The report records the model and settings it ran with; compare them with the deployed configuration.
